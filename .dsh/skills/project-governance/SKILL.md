# 项目治理纪律：版本 · 计划 · 记忆 · 一致性

本技能是本课程项目（无人机-机器狗空地协同巡检集成平台）的**强制工作纪律**。它解决四件事：

1. **随时可回滚**——每一次改动都落入 git 版本库，任何状态都能精确回到过去；
2. **严格分步执行**——所有工作必须登记为计划步骤，一次只做一步、一步一个提交；
3. **持久记忆**——项目事实只存于 `STATE.md`，不依赖对话上下文，会话断了、换了窗口也不丢；
4. **杜绝前后矛盾**——术语、版本、决策只有一处权威来源，改动必须全项目同步。

> 适用范围：本工作区的全部文件（文档、代码、配置、图表）。治理文件本身也受本纪律约束。

## 1. 治理文件（唯一权威）

| 文件 | 职责 | 规则 |
|---|---|---|
| `PLAN.md` | **唯一权威执行计划**。所有工作必须先在此登记为步骤 | 不允许"计划外改动" |
| `STATE.md` | **唯一权威项目记忆**。当前进度、时间线、决策、术语、风险 | 一切事实以此为准 |
| `.gitignore` | 排除构建产物、锁文件、备份目录 | 不提交 `~$*`、`node_modules`、`target` 等 |
| 各交付文档头部「修订记录」表 | 追踪每个正式文档的版本变化 | 每次改文档必须加一行 |

**铁律一**：任何来源（对话记忆、临时笔记、口头约定）与治理文件冲突时，**一律以治理文件为准**。发现治理文件本身有错，先修正治理文件（走提交），再继续工作。

**铁律二**：治理文件的更新与对应工作变更在**同一次提交**中完成，禁止"先干活、回头再补记录"。

## 2. 开场协议（每次会话或每项新任务开始前，逐条执行）

1. `git status` 确认工作树干净。有未提交变更时：属于上一步漏提交 → 立即补提交；属于意外改动 → 先与用户确认处理方式，不得静默丢弃或覆盖。
2. 通读 `PLAN.md`。
3. 通读 `STATE.md`。
4. 交叉核对：PLAN 的"当前步骤"与 STATE 的"当前状态"必须一致。不一致时以 PLAN 为准，在 STATE 时间线记一条"一致性修正"，随下一步提交。
5. 向用户简报：当前版本（tag + 最新提交号）、当前步骤、下一步将做什么。**未得到用户确认，不开始新步骤。**

## 3. 单步执行协议（一步 = 一次提交，全程遵守）

1. **锁定步骤**：只执行 PLAN 中状态为 `in_progress` 的那一步。若无 `in_progress`，取编号最小的 `pending` 步骤，先在 PLAN 中把状态改为 `in_progress`，单独提交（提交信息 `step: Sxx 开始`）。
2. **执行变更**：只做该步骤范围内的事。发现步骤范围之外的必要修改（如顺手的 bug 修复），**不得夹带**——记为待办，事后作为新步骤登记。
3. **验收自检**：对照该步骤在 PLAN 中的"验收标准"逐条自检；不达标继续改，达标才允许提交。
4. **同步治理文件**：
   - PLAN：状态改 `done`（或 `blocked` + 原因）、填写产出物、验收结论、完成时间、提交号；
   - STATE：时间线追加一行（时间、提交号、内容、执行者）；术语/决策有变化时同步更新注册表。
5. **提交**：`git add -A && git commit`，提交信息按第 6 节规范，**一个步骤一个提交**。本步包含里程碑时打 tag（见第 5 节）。
6. **汇报**：步骤号、改了什么、提交号/版本号、下一步预告，然后**停下等待用户指示**。只有用户明确授权"连续执行到 Sxx"时，才在授权范围内连续执行，但每步仍独立提交、独立汇报。

**禁止**：跳步；并行推进两个步骤；一个提交混入多个步骤的改动；完成后不更新治理文件；把"计划外"的内容混入当前步骤。

## 4. 计划管理规则（PLAN.md）

- 步骤编号：`S01`、`S02`… 顺序递增；编号一旦使用**永不复用**。
- 步骤状态：`pending → in_progress → done`（阻塞时 `blocked` + 原因）。
- 新增步骤：只能追加在计划末尾；确需插队时，标记 `插入` 并写清理由，且**必须经用户确认**。
- 回滚本身也是一个步骤：在 PLAN 登记"回滚至 xxx"，执行后照常更新治理文件并提交。
- 每步必须包含四要素：**目标 / 内容 / 验收标准 / 产出物**。验收标准必须可判定（对/错），不得写"基本完成""大概可以"。

## 5. 版本与回滚协议

### 5.1 版本规则

- 版本 = git 提交 + 里程碑 tag。tag 命名 `v0.1`、`v0.2`…，与 STATE 中登记的版本号一致。
- 里程碑 = PLAN 中标注"里程碑"的步骤（如：方案定稿、原型可跑、联调完成、测试通过）。
- 备份 tag：任何大动作（重构、批量替换、环境变更）**动手前**先 `git tag backup-YYYYMMDD-HHMM`。

### 5.2 回滚操作（按场景选）

| 场景 | 操作 | 效果 |
|---|---|---|
| 回退某一步骤的全部改动，且其后续有工作 | `git revert <提交号>` | 生成新提交，历史完整 |
| 只恢复个别文件到历史版本 | `git checkout <提交号> -- <文件路径>` 后提交 | 只动该文件 |
| 临时查看历史状态 | `git show <提交号>:<文件>` 或 `git worktree add` | 不动主线 |
| 回退后反悔 | `git revert <回滚提交号>` | 回滚的回滚，依然可逆 |

- 回滚**也是提交**：回滚动作登记为计划步骤，执行后在 STATE 时间线写明"回滚了什么、为什么、回滚后状态"，然后提交（提交信息 `rollback: ...`）。
- 回滚前先 `git log --oneline` 看清目标；拿不准时先打备份 tag。

### 5.3 危险动作黑名单（**绝对禁止**，或须用户明确同意）

- `git reset --hard`（丢工作区）、`git push --force`、删除 `.git`、改写已提交历史（rebase/amend 已存在的提交）；
- `docker compose down -v` 及任何删除数据卷、删除备份的操作；
- 删除 `PLAN.md` / `STATE.md` / 本技能文件；
- 全项目批量替换（sed 式）、批量移动/重命名文件——除非已作为计划步骤登记并经用户同意。

## 6. 记忆与防上下文矛盾协议

### 6.1 STATE.md 必备区块（缺一不可）

1. **当前状态摘要**：当前步骤、最近完成、进行中事项；
2. **版本表**：tag / 提交号 / 内容摘要 / 日期；
3. **变更时间线**：每条 = 时间 + 提交号 + 内容 + 执行者，只增不改；
4. **决策记录 D-n**：决策内容、理由、状态（`有效` 或 `被 D-m 取代`+取代理由）。**旧决策永不删除，只能标记被取代**；
5. **术语与口径注册表**：组件版本、端口、主题名、集合名、编号段、指标约定——全项目只有这一处权威口径；
6. **已知问题与风险**：未解决问题、`【待回填】` 清单、排错预案索引；
7. **下一步计划**：与 PLAN 的下一步一致。

### 6.2 写作前的防矛盾检查（涉及既有事实的任何修改，必须先做）

1. `grep` 相关关键词，找出全项目所有引用点；
2. 确认新写法与注册表、决策记录、既有章节口径一致；
3. 若必须改变口径 → 顺序固定：**先**更新注册表、**再**登记新决策 `D-n 取代 D-m` 并写清理由、**最后**修改所有引用点——三者同一提交；
4. 数字、编号、版本号（端口、主题名、用例号、图号、指标）一律以 STATE 注册表为准，**不凭对话记忆**。

### 6.3 修订记录

每次修改正式交付文档（课程设计报告、任务书等），在文档头部「修订记录」表新增一行：日期、版本、修订摘要、对应提交号。文档正文开头保留"本版本对应提交号"一行，实现文档 ↔ git 双向可查。

### 6.4 矛盾处置

发现 PLAN / STATE / 实际文件三者不一致，或文档前后文矛盾时：**立即停下**，向用户说明矛盾点与处理方案，确认后修复；并把"矛盾发现 + 解决方式"记入 STATE 时间线。**禁止带着已知矛盾继续产出内容。**

### 6.5 收尾自检（每次汇报前，逐条过）

1. 提交干净（`git status` 无未提交变更）；
2. PLAN 与 STATE 已更新且互相一致；
3. 若改了术语/编号/决策，注册表与全部引用点已同步；
4. 汇报内容与 STATE 记录完全一致。

## 7. 提交信息规范

| 类型 | 格式 | 示例 |
|---|---|---|
| 步骤主提交 | `step: Sxx <动宾短语>` | `step: S05 完成告警消费者与幂等消费` |
| 文档 | `docs: <内容>` | `docs: 课程设计报告补第 3.5 节用例图` |
| 修复 | `fix: <问题>` | `fix: ES 坐标经纬度顺序颠倒` |
| 工程杂项 | `chore: <内容>` | `chore: 更新 .gitignore` |
| 回滚 | `rollback: <回滚内容与原因>` | `rollback: 撤销 S08 的索引重建，原因见 STATE` |

- 一步一提交；提交正文可选，用于说明与验收标准的对应关系；
- 里程碑提交打 tag：`git tag v0.2 && git push`（有远端时）；
- 步骤开始标记提交：`step: Sxx 开始`。

## 8. 常用命令速查（Windows PowerShell）

```powershell
git status; git log --oneline -10; git diff; git show <提交号> --stat
git tag; git tag v0.3; git revert <提交号>
git checkout <提交号> -- <文件路径>; git stash list
git tag backup-$(Get-Date -Format yyyyMMdd-HHmm)   # 大动作前打备份 tag
```

## 9. 加载与使用方式

- 需要时向 AI 说"按项目治理纪律来 / 加载 project-governance / 下一步做什么 / 回滚到 xxx"，或在动手前主动加载本技能；
- 本技能文件路径：`.dsh/skills/project-governance/SKILL.md`，与项目同库、随项目走；
- 若小组多人协作：任何成员提交前必须过第 2 节开场协议与第 6.5 节收尾自检；治理文件冲突时以 `STATE.md` 为准、经讨论后修正。
