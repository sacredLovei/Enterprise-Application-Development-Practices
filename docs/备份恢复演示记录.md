## 1. 演示目标与验收口径

| 项 | 口径 |
|---|---|
| 目标 | 证明 S79 产出的备份产物**可真实恢复**，恢复后数据与代码与备份时刻一致 |
| 恢复对象 | ① MongoDB `inspection` 库（业务权威数据源，决策 D-5）；② 代码版本库（含全部历史与标签） |
| 一致性判定 | 逐集合文档计数「原库 == 恢复库」，全部相等记 `MATCH`；代码库比对 HEAD 提交号与 tag 数量 |
| 通过标准 | 6/6 集合 `MATCH` 且 HEAD、tag 数完全一致 → `PASS=2 FAIL=0` |

## 2. 演示环境

- 平台：Docker Compose 单机部署，**13 容器**：namenode / datanode / mongodb / kafka / elasticsearch / kibana / nginx / backend-1 / backend-2 / uav-sim-1 / uav-sim-2 / dog-sim-1 / dog-sim-2（本次实测 `docker ps` 计数）
- MongoDB 6.0 副本集 `rs0`（单节点），库名 `inspection`，集合：`device`、`device_status`、`task`、`task_log`、`alarm`、`image_meta`
- 恢复验证时间：**2026-09-21 11:47**，备份批次标签 `20260921-114627`

## 3. 演示流程（脚本实际执行顺序）

| 序 | 动作 | 命令要点 |
|---|---|---|
| 0 | **暂停全部写入方**（4 个仿真 + 2 个后端实例），等待 8s | `docker compose stop uav-sim-1 uav-sim-2 dog-sim-1 dog-sim-2 backend-1 backend-2` |
| 1 | 导出业务库 | `mongodump --db inspection --out /tmp/s87` |
| 2 | 恢复到**临时库**（不覆盖生产库） | `mongorestore --nsFrom 'inspection.*' --nsTo 'inspection_restore.*' /tmp/s87` |
| 3 | 逐集合计数比对 | `db.<集合>.countDocuments()` 两侧各取一次 |
| 4 | 清理临时库 | `db.dropDatabase()` on `inspection_restore` |
| 5 | **恢复写入方**（后端+仿真启动、健康等待、重启 nginx） | `docker compose start …` + `docker compose restart nginx` |
| 6 | 代码库备份 | `git bundle create _backups/<tag>/repo.bundle --all` |
| 7 | 克隆恢复并校验 | `git clone repo.bundle <临时目录>` → 比对 `rev-parse HEAD` 与 tag 数 |

**关键设计说明（实测得出）**：第 0 步必须同时暂停**仿真与后端**。首轮仅暂停仿真时，`alarm` 集合出现 `1279 vs 1278` 的 1 条差异——原因是设备心跳停止后后端离线检测器在导出窗口内补发了一条 `DEVICE_OFFLINE` 告警（导出期间仍有写入）。改为完全静态窗口后 6/6 全部一致，此坑已登记 STATE 风险 #40。

## 4. 实测结果

### 4.1 MongoDB 恢复一致性（原库 → 恢复库）

| 集合 | 原库计数 | 恢复库计数 | 判定 |
|---|---|---|---|
| device | 4 | 4 | MATCH |
| device_status | 116,439 | 116,439 | MATCH |
| task | 181 | 181 | MATCH |
| task_log | 524 | 524 | MATCH |
| alarm | 1,282 | 1,282 | MATCH |
| image_meta | 1,398 | 1,398 | MATCH |

结论：`MONGO_ALL_MATCH=True`，**6/6 集合计数一致，恢复数据完整**。

### 4.2 代码版本库恢复校验

| 指标 | 原库 | 克隆恢复库 | 判定 |
|---|---|---|---|
| HEAD 提交号 | `3b92b7ce8fa187f6dbb4ac59eb5db5e330a72b2f` | 同左 | 一致 |
| 标签数量 | 7（v0.1~v0.7） | 7 | 一致 |
| bundle 体积 | 0.73 MB | — | — |

结论：单文件 `repo.bundle` 即可在任意机器完整还原代码库与全部里程碑标签。

## 5. 复现命令

```powershell
cd docker
# 1) 产出备份（_backups\<时间戳>\：repo.bundle + mongo/ + compose.yml）
powershell -NoProfile -ExecutionPolicy Bypass -File .\init\backup.ps1
# 2) 备份产物恢复验证（静态窗口导出 → 恢复临时库 → 比对 → 清理 → 恢复写入方 → bundle 克隆校验）
powershell -NoProfile -ExecutionPolicy Bypass -File .\init\restore-demo.ps1
```

脚本以纯 ASCII 编写（规避 PowerShell 5.1 按 GBK 读取脚本的编码坑，STATE 风险 #16），可直接在中文/英文 Windows 上运行。

## 6. 恢复能力结论与已知边界

**结论**：本项目备份产物具备**可验证的恢复能力**——业务库恢复后各集合计数与原库逐一相等；代码库可由单文件 bundle 完整还原。恢复演练本身可重复执行（脚本化、无人工步骤），满足课程对"恢复验证"的要求。

**如实记录的边界（不夸大）**：

1. 本次验证覆盖 **MongoDB 业务库 + 代码库**；Elasticsearch 检索索引与 HDFS 影像数据未纳入本次恢复验证范围。ES 为检索副本（决策 D-5），数据可由 MongoDB 重放/重建（对账补偿接口 `POST /api/maintenance/reconcile`）；HDFS 数据位于 Docker 命名卷（`hadoop_namenode`/`hadoop_datanode`），由 Docker 跨重启保留，卷级备份在 `backup.ps1` 中已注明但未自动化。
2. 演示采用**临时库恢复 + 计数比对**（非原地覆盖恢复），即验证"备份产物可用"，不验证"生产库被破坏后的原地回灌流程"；原地回灌命令为 `mongorestore --drop --nsFrom 'inspection.*' --nsTo 'inspection.*'`。
3. 比对口径为**集合文档计数一致**（配合静态写入窗口）；未做逐文档字段级 diff，如需更严格比对可用 `mongodump` + `bsondump` 逐文档哈希。
4. 单机单节点部署，未涉及跨机房容灾与增量备份（不在课程范围）。
